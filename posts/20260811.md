## Lesson: a guard that cannot fail proves nothing — run every test, gate and fixture against the broken world before trusting it

**Trigger:** adding a test, a CI gate, or a negative fixture; or writing a
comment/doc sentence that asserts a property.

**Root:** both halves below are the same error — **claiming more than has been
established.** The 20260805 post covers the review-side direction (verify a
finding against reality before posting). This is the authoring-side direction:
verify your own evidence can distinguish before trusting it.

---

### Half 1 — vacuity. Seven instances in one workstream (PR #719, Case 2)

A negative assertion is satisfied by *any* failure, so it passes for the wrong
reason constantly:

1. **SIGINT test** — background job started with SIGINT ignored; the kill
   tested nothing. (π caught)
2. **Missing tool** — `cue` absent from PATH, so all 21 corpus negatives
   printed `✓ rejected` because the binary did not exist. (self-caught)
3. **Empty hole domain** — a `$skill` hole with no domain expanded to zero
   refs; neighbouring fixed refs kept `checked > 0` and the closure test green.
   (π)
4. **Multiply-invalid fixture** — `cellspec-bad-param-name.json` had a
   required-unfilled param AND a bad stub field, so it returned exit 2 for
   reasons other than the name it was named for. (π)
5. **Shared exit code** — `run_bad` accepts exit 2, which is also the runner's
   missing-contract exit AND the unresolvable-base-SHA exit. The fixture proved
   refusal, not cause. (π)
6. **Wrong object** — a malformed-hole test inserted an illegal *declared key*,
   which `Parse` rejects before any seat value is read. Malformed-hole handling
   could have been deleted with every test still green. (π)
7. **Non-witnessing witnesses** — three fixtures written to prove a CUE/Go
   divergence; checked against the *old* definition and found the negative was
   rejected for an unrelated reason and both positives already passed.
   (self-caught, before shipping)

Five of seven were caught by β, not by me. The two I caught were caught by
applying the rule below — it works when actually applied.

**Rule (imperative):**
- Before accepting ANY guard, **break the thing it guards and watch it fail.**
  Delete the check, revert the fix, remove the fixture, unset the tool — then
  confirm the guard reports the failure you expect, with the diagnostic you
  expect.
- For a negative fixture, make it **singly invalid**: the same fixture with the
  single defect repaired must PASS. If it still fails, it is not a witness for
  its own claim.
- Where a failure code is shared (exit 2 for "rejected" and "file missing"),
  assert the **reason**, not the code.
- A `checked == 0` counter is the minimum, not the discipline.

### Half 2 — overclaim in prose. Same root, different surface

Nine review rounds; roughly half the findings were sentences in code comments,
docs and PR bodies asserting more than the implementation delivers:
"nothing inherited from the host", "no ambient settings", "every value is
re-derived", "a one-byte edit fails", "cellcog is a generic cognition
subsystem", a `$PATH`-style resolver that was never built, a byte count that
was actually a code-point count.

Dense justification comments were the generator: each sentence became an
auditable claim, and I wrote a lot of them.

**Rule (imperative):**
- Write the comment that explains **why**, not the one that advertises a
  guarantee. If a sentence states a property, it must be a property something
  checks.
- **When a claim needs qualifying a third time, delete it.** The held
  CDD-promotion section was narrowed twice and still contradicted itself; the
  honest size of an unsupported claim is zero. Deletion is a first-class move
  (`eng/evolve §3.8`).
- Say what the gate checks, name what it does not, and label the rest
  transcribed or observed.

**Payoff:** β rounds collapse. Nearly every round on PR #719 after the
mechanism converged was one of these two classes; the mechanism itself
(~150 lines: argv builder, bounded subprocess, skills into a prompt) was never
the problem.

## Lesson: withholding a capability is not containment — it only removes the seat's ability to check itself

**Trigger:** narrowing what a rented seat may do, "to be safe".

I set the producing seat's tool surface to `Read,Write,Edit,Glob,Grep` and
defended it through several rounds as a boundary — in a package that disclaims
confinement in every other comment. The live dispatch workflow this cell is meant
to mechanize allows `Bash`. The operator caught it with one question: *what is the
point of a cell that cannot do the work needed?*

The tell was already in the evidence and I had read it as success: the only real α
episode wrote a Markdown file. Prose is what an unverifying seat can honestly
finish. A seat that cannot run `go test` produces plausible code it has no way to
check, and then the review round has to do the checking.

**Rule (imperative):**
- A restriction is only a boundary if something ENFORCES it. Offering fewer tools
  to a process that can already reach the host is a capability declaration, not
  containment — write it as one.
- Availability is not approval, and they need separate flags. `--tools` bounds what
  exists; `--allowedTools` grants permission for what exists. The earlier "must
  never appear" rule against `--allowedTools` was over-generalized from a real
  defect (it used as a REPLACEMENT for `--tools`) and cost a capability.
- Before generalizing from one measurement, ask what the measurement actually
  touched. `echo X > file` proved the edit path, not the shell; `go version` was
  denied. One narrow probe promoted to a general claim is the same overclaim
  failure as any other.

## Lesson: an independent reviewer given an insufficient input does not abstain — it invents

**Trigger:** designing a review seat's input, or reading a β finding that cites
something you cannot see.

In the first live Case-3 episode β returned a BLOCKING finding: a file was missing
a `bytes` import. The file imports it at line 126. β has no tools by design and the
worktree is released before it runs, so it had 13,782 bytes of diff and no way to
look — and it produced a confident, specific, false claim rather than saying it
could not tell.

This is not a model defect to prompt around. It is a CONTRACT defect, and
`cdd/issue/proof` already names it: β must be able to verify without recovering
hidden context, and the failure mode is *false closure*. The contract that episode
ran under had `goal: "Carry out the change described by the issue…"` — referring to
an issue the cell was never given. Nothing stated the acceptance criteria, so
nothing constrained the verdict.

**Rule (imperative):**
- Design the reviewer's input FIRST, from what a verdict must rest on. If the
  reviewer cannot check a criterion from what it is handed, either hand it the
  means or drop the criterion — do not hope.
- Make "I could not verify this" a representable outcome. A verdict type of
  `pass | fail` forces a guess; `pass | findings | unverified` does not.
- Push cost into the ISSUE, not the review. A well-formed issue — criteria each
  naming their verification route — is what makes verification cheaper than
  production. An under-specified issue relocates the whole design problem into the
  review round, where there is less context to solve it with.

## Lesson: sort your defects by what would have caught them, and the design doc writes itself

**Trigger:** a workstream where review keeps finding real defects. Before
concluding "review is working", ask when each defect became *knowable*.

Eight defects in this workstream. Every one was found after the code existed —
by β, by the operator's question, or by a mutation test — and every one was
decidable from a written design. Sorted by what would have caught them:

- **A — untraced value flow.** A value is produced at one station and consumed
  at another and nobody wrote the path. `cellwork.Diff` measured against HEAD
  because `base_sha` was pinned at materialization and then not used at
  measurement; `Contract.Task` reached the record without anyone tracing that
  `episode-closure.cue` closes `contract`. *Catcher: a table of every value
  crossing a boundary — producer, consumers, and every schema surface it must
  appear in.*
- **B — enforces vs declares was never stated.** Three defects, all the same
  missing sentence. See the capability-withholding lesson above; add
  `--tools` (availability) mistaken for `--permission-mode` (approval), and an
  issue-admission barrier put in `#CDSCellSpec` so it leaked into 17 fixtures
  that pass that door for unrelated reasons. *Catcher: per component — what it
  enforces, what it declares, what it claims nothing about; per barrier, where
  it sits and what it does not follow into.*
- **C — a seat asked to decide what its input cannot decide.** See the
  false-review lesson above. *Catcher: per seat — the decision, the input, the
  ARGUMENT that the input suffices, and the representable outcomes including
  inability to decide.*
- **D — parity restated by hand.** Dual authority realised by writing each rule
  twice and hoping. `#NonBlank: =~"\\S"` was documented as "the CUE half of
  `strings.TrimSpace`" and is not — RE2's `\s` is ASCII-only, so eight
  whitespace runes were admitted by CUE and rejected by Go. *Catcher: per rule
  — owning authority, mirroring authority, and the mechanism that CHECKS they
  agree, never the sentence claiming it.*
- **E — unspecified oracle provenance.** The shared corpus never built `cn`; it
  ran whatever binary sat in the repo root. CI builds first and was fine, so
  only LOCAL runs were measuring a stale artifact — which means some of my own
  "corpus green" reports were weaker evidence than I presented them as. Found
  only because a mutation test reported green after I deleted the guard it was
  testing. *Catcher: per oracle — how the artifact under test is obtained, and
  what green does and does not prove.*

**Rule (imperative):**
- When review finds a real defect, record WHEN it became knowable, not just
  what it was. A defect knowable at design time and found at review time is a
  design-process failure wearing a review-process success.
- The five classes above are a checklist, not a taxonomy to admire: value flow,
  enforces-vs-declares, decision sufficiency, rule ownership, oracle
  provenance. Answer them before coding and most of a design document exists.
- A design document that cannot be wrong is the same failure as a test that
  cannot fail. Every section must be checkable against the code.
